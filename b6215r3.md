## What and why

Fixes #6125, fixes #6354. Both issues ask for the same vanilla call, `LevelAccessor.scheduleTick(pos, block, delay, priority)`, from two places. A mod cannot queue a scheduled tick from a server hook (#6125). `LevelTicksHost::schedule_block_tick` exists only on the in-line hosts, and it has no priority (#6354).
- #6125: Blood Magic's Sigil of the Frost places frosted ice and calls `level.scheduleTick(pos, Blocks.FROSTED_ICE, Mth.nextInt(random, 60, 120))`, as vanilla's Frost Walker does. Without it the port's ice gets no first melt tick, melts from random ticks only and lasts longer than in Java.
- #6354: a `BlockPart::neighbor_changed` gets `&mut dyn LevelWriteHost`, not a `ServerHost`, so it cannot schedule at `HIGH`, `VERY_HIGH` or `EXTREMELY_HIGH` as `DiodeBlock.checkTickOnNeighbor` does. Create's `GearshiftBlock` reattach needs `EXTREMELY_HIGH` there too.

One design: one engine call, one queue, one priority type, two entry points.
- `TickPriority` (new, `sunrise-mod-vocab` `world/types.rs`): `ExtremelyHigh` to `ExtremelyLow`, default `Normal` (`net.minecraft.world.ticks.TickPriority`). `TickPriority::value()` is `getValue()`, and the game converts by that value, so no variant falls through to `Normal`.
- From any server hook, on `LevelRef`: `schedule_block_tick(host, pos, block, delay, priority)` and `schedule_fluid_tick(host, pos, fluid, delay, priority)`, both `-> Result<bool, LevelWriteError>`.
- From an in-line level writer (`neighbor_changed`, `tick_block`, `update_shape`), on `LevelTicksHost`: `schedule_block_tick_with_priority(pos, block, delay, priority)` and `schedule_fluid_tick_with_priority(pos, fluid, delay, priority)`, both `-> bool`. Every `LevelWriteHost` has them. The existing `schedule_block_tick` and `schedule_fluid_tick` keep their signatures and queue at `Normal`.
- Both entry points end in the same function, `api_values::schedule_block_tick` / `schedule_fluid_tick` in `sunrise-client`, which writes `Ticks::schedule_block` / `schedule_fluid_with_priority`. Inside a transaction the tick is a pending journal write (an engine fluid for a fluid tick) and goes into the same queue at commit. Both `LevelRef` calls use the same transaction check.
- Name: the codebase has no tick-options struct, and its host traits name a variant `verb_with_noun` (`hurt_with_source`, `run_command_with_output`). So the in-line method is `schedule_block_tick_with_priority`, beside the old call that `update_shape` hosts already use.

Behaviour, both entry points (`ScheduledTickAccess.scheduleTick`, which `LevelAccessor` inherits):
- The tick is saved with the chunk. A block tick is ignored when the block at `pos` is no longer `block` as it comes due.
- Run order, as `LevelTicks.collectTicks`: a chunk's own queue runs by trigger tick, then priority, then the order scheduled. Across chunks there is no single order: each chunk with a due tick competes by its next tick's priority, then the order scheduled, not by trigger tick. So ticks due on the same game tick run by priority, then the order scheduled, in every chunk, but when ticks of different trigger ticks are due together (a chunk that could not tick, a pass over its budget), an older `Low` tick in one chunk can run after a newer `High` tick in another. The docs on `LevelRef::schedule_block_tick`, `TickPriority`, `LevelTicksHost::schedule_block_tick_with_priority`, `hooks/level_reads.rs` and the change note say this.
- `true` / `Ok(true)` when queued or already queued. The queue keeps one tick per type and position (`LevelChunkTicks.schedule`), so a repeat with another delay or priority is dropped and the first keeps its deadline and priority.
- False / `Ok(false)` when the chunk has no tick container (unloaded, or loaded with no tick list yet), or for a block or fluid with no world form. The height is not checked, as `LevelTicks.schedule` checks only the container. `LevelRef` also refuses a cell a carrier transfer holds, as every mod write does, and returns `Err` for a stale handle, a client or a level not in place.
- Through `LevelRef` inside a transaction the tick waits in the journal and its delay counts from the commit.
- Engine: `Ticks::schedule_fluid_with_priority` is new; `schedule_fluid` calls it at `Normal`. The journal's pending `BlockTick` and `FluidTick` writes carry a priority, and the command block path passes `Normal`.

Tests (daily):
- `world_fluids_tests::a_mod_schedules_block_and_fluid_ticks_in_the_level_queue`, the `LevelRef` path, in its own child process. A loaded chunk with no tick container gives `Ok(false)`. A block tick and a `High` fluid tick land in the level's queues. A repeat with another delay and priority is `Ok(true)`, and the one tick keeps the first deadline and priority, also when the first was scheduled in a transaction. A position above the build height is queued, an unloaded one is not, and a stale handle is `Err(Stale)`. Inside `storage_scope` the tick waits for the commit, and an abort drops it. A `VeryHigh` fluid tick scheduled in a transaction is in the fluid queue after the commit at that priority, its delay counted from the commit, and an abort leaves the fluid queue empty there. Two ticks due together, `Low` scheduled first, run `High` first, both directly and when a transaction queued them.
- `native_entity_refs::tests::a_part_schedules_a_high_priority_tick_from_neighbor_changed_that_runs_first_next_tick`, the in-line path (#6354). A vanilla repeater's scheduled tick powers it, and its `onPlace` (`updateNeighborsInFront`) calls a native glass part's `neighbor_changed`. The part schedules its own tick at `High` with delay 1, and it does not run in that tick. On the next tick it runs before a `Normal` glass tick due then, which was queued earlier. With `Normal` the order would be the reverse. The same `neighbor_changed` queues a water tick with `schedule_fluid_tick_with_priority` at `VeryHigh`, delay 5, and the fluid queue holds it at that priority and deadline.
