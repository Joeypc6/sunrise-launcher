## What a mod needs

A container screen that the player can drag by its edge, as some Java mods do. Their `AbstractContainerScreen` subclass changes `leftPos`/`topPos` while the screen is open (from `mouseDragged`), and everything moves with the window: the background, the slots, the hit tests, the tooltips and the labels. Other uses: a screen that remembers where the player left it, or one that steps aside for a tall side panel.

Example: a reactor control screen in a mod in development is draggable by its top three pixels. In the port the window stays centred.

## What happens on main (c59f592366)

- `MenuScreenLayout` (`client/types.rs`) gives a mod screen its `width`, `height`, `slots`, `inventory_x`/`inventory_y`, its labels and a recipe book. The game centres the window itself; nothing sets or offsets its origin.
- `MenuScreenFrame::origin` reports the panel's top-left corner, read-only.
- `ScreensClientHost::set_screen_slot(menu, slot, pos)` moves one slot within the window but not the window.
- `screen_room(screen, left, right)` asks for room beside the window, and the game re-centres the window horizontally to fit it. That is a layout request, not a position: it is asked once a frame, can't move the window vertically, and does nothing when the parts don't fit.
- The engine already rebuilds the layout when the origin changes. The container build compares `image` and `origin`, and the slots, recipe book, effect panels and exclusion areas move with it, so a moved window would stay consistent.

## Proposal

An offset from the centred position, held for this opening of the screen:

```rust
/// Moves the open screen of mod menu type `menu` by `offset` GUI pixels from where the game
/// centres it (vanilla's `leftPos`/`topPos` changed by a subclass), from the next frame. The
/// slots, labels, recipe book, effect panels, hit tests and exclusion areas move with it.
/// Cleared when the screen closes. Refused with no such screen; a non-finite offset is refused.
fn set_screen_offset(&self, menu: &str, offset: [f32; 2]) -> Result<(), ScreenSlotRefusal>;
fn screen_offset(&self, menu: &str) -> Option<[f32; 2]>;
```

A mod handles the drag itself with `screen_mouse_button_pressed_pre`, `screen_mouse_dragged_pre` and `screen_mouse_button_released_pre`, as the Java screen does in `mouseClicked`/`mouseDragged`. Whether to clamp the window to the GUI is the mod's choice, as in vanilla. If the `screen_room` re-centring applies too, the offset adds to that position.

## Vanilla / NeoForge reference

- `AbstractContainerScreen.leftPos`, `topPos` (protected fields, set in `init()` and free to change later); `renderSlots`, `isHovering` and `hasClickedOutside` all read them.
- NeoForge has no event for it; mods subclass the screen and set the fields.
