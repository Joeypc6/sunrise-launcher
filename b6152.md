## What and why

Fixes #6120. Load a mod whose data has its own damage types (`data/<mod>/damage_type/*.json`) and lists them in vanilla damage-type tags (`data/minecraft/tags/damage_type/bypasses_armor.json` and others). Tinkers' Construct does this in ten tag files, and Sunny Evolution needs the same. The game then logs `damage tag minecraft:bypasses_armor has unresolved required entries` for 17 vanilla tags and drops each of those tags whole, vanilla's own entries included.

**Cause.** The content-mod resource root (`mod_content::build_with_conditions`) merges every mod tag file into the root's tag files on disk, damage-type tags included, so the root's `bypasses_armor.json` names `tconstruct:bleeding`. The mods' registry files are different: their damage type definitions stay only in the passive data layers (`resolved_resources`), which the world's pack stack reads. A loader that reads the root alone therefore binds tags that name the mod's types against a registry without them. The warnings come only from those loaders: `load-core` (the startup `HealthResources` catalog), `Structure mobs` (the structure-mob tables' items and enchantments) and `Server data preload` (the client sync preload). The world-open path reads the pack overlay and is silent in every Tinkers log checked.

**Fix.** The root builder now also writes each mod's winning `data/<ns>/damage_type/<path>.json` into the root, next to the merged tag files. A later layer's file wins, as in a pack stack. The root's readers (`Items::catalog(root, &PackOverlay::NONE, ...)`, the startup catalog, the sync preload) evaluate files with the vanilla-only inventory, so the builder decides the winning file's `neoforge:conditions` once, with the owning load's conditions, as it does for the worldgen and modifier files: a file that fails them is left out, a file that holds is written without the key (`neoforge:value` unwrapped, from the raw text so numbers keep their decimals). The root's damage registry and its tags then come from the same set of packs, so `TagLoader` resolves the mod's entries and the tag keeps vanilla's types too. A missing required entry still fails only its own tag file, through the unchanged `TagDefinitions::build`, and still logs the warning. A malformed damage type file now fails the root build, naming the mod and file, like a malformed modifier file; vanilla's `RegistryDataLoader` fails the load on it too, and world open already failed on it.

Files:
- `crates/sunrise-client/src/mod_content/load_conditions.rs`: collects the mods' damage type files in the data-file loop (new `is_damage_type_file`), evaluates the winners' conditions and writes them into the root (new `without_conditions`).
- `crates/sunrise-client/src/mod_content_load_conditions_tests.rs`: two tests, read through the root alone (`Catalog::with_packs(root, &PackOverlay::NONE)`, and for the first also `resource_tags` over `resource_files` names, as `lan/data.rs` does):
  - `a_mod_damage_type_in_a_vanilla_damage_tag_keeps_the_tag_bound`: a mod type in `minecraft:bypasses_armor` keeps vanilla's two members and adds its own.
  - `a_gated_mod_damage_type_is_decided_once_for_the_root_alone_readers`: a type gated on `neoforge:mod_loaded` and one gated on `neoforge:not` of it, with the other mod present and absent.

A later mod winning a file and a mod replacing a `minecraft:` definition are not tested: `check_namespace` refuses a mod file at `data/minecraft/damage_type/`, and two mods can't own one namespace, so neither reaches the root builder. The builder still keeps the later layer's file within one mod.

The client side needs no change. A remote client or LAN guest binds the server's `UpdateTags` against the synchronized registry names (`remote_tags.rs`), and the server builds those from the root plus the overlay, which now agree.

## Layer

Content-mod resource root build (sunrise-client). No mod API change and no new dependency. Existing roots are rebuilt because the game build is part of the root's stamp.

## Vanilla reference

`RegistryDataLoader.load` reads every pack's `damage_type` entries, mod data packs included, into the frozen `Registries.DAMAGE_TYPE` before `TagLoader.loadTagsForExistingRegistries` / `TagLoader.build` bind `tags/damage_type`. A tag's required entry resolves against that full registry (`Registry` tag binding through `HolderLookup`), and an entry missing from it fails only that tag.
