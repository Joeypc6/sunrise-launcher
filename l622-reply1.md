**1. Prove the installed image (`src/native_mods/reuse.rs`).** The parallel key (`native-inputs-v1`), the `.native-inputs` file and the 7-character prefix scan are gone. `version_for` is the one identity again:

- The lookup copies the mods into a private folder first (`reuse::before_planning`, and in `pipeline` the lookup now runs on the planned path's own `mods.incoming` copies, `src/native_mods.rs:1643`). From that copy it works out the version as planning does (`reuse::derive`, reuse.rs:298): `kept_mods`, the override-aware graph, `build_revision`, the pins through the same `mixins::read_pins` the plan uses (mixins.rs:35) but from SDK indexes already kept on disk only (`sdk_cache::kept`, sdk_cache.rs:380, nothing fetched), `materialize` on the copies, `for_key` with kept commit dates only, then `version_for` itself. The candidate is the directory with exactly that version, so both sides hash the same kind of bytes (staged, materialized copies), and nothing hashes live files against a record taken from copies.
- The proof (`reuse::lookup`, reuse.rs:380): `.native-reuse.json` (`EVIDENCE`) must name that version and hold the same `Image` (below); `native-mods.json` must name the revision, the starting release, the horizon-mixins key, the profile and the left-out set, `native_status::included` (the check Play uses) must list exactly the kept mods at their versions and source digests, and the installed `sunrise-native-mods/` must hold exactly their copies (`Contents::installed_in`, reuse.rs:153); and `managed_play::Artifact::capture_at` of the directory (executable, `native-mods.json`, `deps/`, native trees and every library beside the game) must equal the seal kept in the evidence. The missing executable and invalid record of the old positive test now both miss (`an_installed_build_that_changed_misses`).
- What is missing: native installs publish no receipt today. `Artifact::record_archive` and `record_sdk` seal release installs at extraction, but `installation::install` writes nothing comparable. So the seal is taken by the planned path right after `publish_build` (or, for an image an older launcher installed, at the first reuse after its contents check). An image changed between its install and that first record can't be told apart. A publish-time receipt for native builds would close that, and it belongs with the install path rather than this PR. I can do it as a follow-up if you want.
- Image inputs and validation-only rules are separate types. `Image` (reuse.rs:43) is what changes the build without being in its version: each kept mod's pin, the Cargo link order the tool gets, the override-aware dispatch order (now returned by `resolve_build_dependencies`, native_mods.rs:1431, instead of being checked and dropped), the left-out ids, and the SHA-256 of each signed SDK index (and the developer SDK's index) the plan read. `Admission` (reuse.rs:94) only admitted the plan: the launcher version (its checks), the base and starting release, an exact profile build, and `SUNRISE_SDK_BASE`. One build keeps up to 8 admissions. Tests: `an_input_that_changes_the_build_misses_it`, `another_dispatch_order_misses_the_build` (a `load_before` dropped by an override changes only the dispatch order and misses), and `a_rule_that_only_admits_the_plan_misses_until_it_admits_it`.
- A change between lookup and admission: once the build is proved, the lookup derives everything again from the copy and the profile as they are then (mod list, content packages, overrides, kept indexes), and compares the mods' folder with the copy by source digest. Any difference misses (reuse.rs:407). After that, Play's own `verify_included` / `check_compiled_profile` still compare the build with the live profile, as for a planned build.
- On the dispatch order: as far as I can see, the build itself gets only the Cargo order (`ordered`), and `version_for` covers neither order. I bind the dispatch order in the evidence anyway, so an override change misses even if it turns out not to change the binary.

**2. Record only what the image used (`src/native_mods.rs:1885`, reuse.rs:228).** First, the bug itself on `main`: `pipeline` names a build from every requested mod, so a reduced retry was installed under the whole set's version, and a later whole-set plan found it and said "Up to date". Regression test: `native_mods::tests::a_build_that_leaves_a_mod_out_never_has_the_whole_sets_version`. It names the set with and without a mod left out as `pipeline` does and requires two versions. Run once in our build queue with the salt taken back out of `version_for` (`main`'s hashing), it failed with `native-aaaaaaa-448598e378db` for both. With the salt, it passes.



- `version_for` now salts its hash with the left-out ids when there are any (native_mods.rs:735 on the first commit, 742 on the second). A reduced build gets its own version, and a whole set's version is the same as before, so installed builds aren't rebuilt.
- The evidence is written from the verified plan (pins, both orders, left-out set, and the SDK digests from the `Sdk` values the plan consumed, via `read_pins` and `sdk.signed()`, nothing re-read afterwards). It is written only when `Contents::installed_in` holds for the installed directory. That runs in both branches: after install, and in the existing-image branch, which before checked only `.installed`. A reduced image an older launcher installed under the whole set's version gets no evidence and keeps being planned as on `main`. The write is whole-or-nothing (`sdk_cache::write_whole`).
- Tests: `a_reduced_build_never_satisfies_the_whole_set` (both versions, and the older launcher's reduced image under the whole tag) and `missing_torn_or_older_evidence_plans_the_build` (missing, torn, other schema, unknown field, and the 98b2edc `.native-inputs` file all plan the build).

**3. Reuse before the default SDK check (native_mods.rs:2432).** `build` now tries `reuse::before_planning` before `select_build_profile` → `planning::classify`, with the profile the automatic choice resolves to (`AUTOMATIC`). Whatever stops it (an unprepared base, a duplicate id) finds nothing, so the error text and order stay as today. `the_default_build_uses_an_installed_set_without_the_sdk_check` goes through `build` itself in a scratch home, counting `check_all` calls (a test-only per-thread counter, not progress steps). A hit makes 0 SDK checks, says only `Plan(UpToDate)` and points the instance at the build. With the evidence removed, the same call makes 2 (the profile check and the build's own). I think this is why my Windows numbers showed only 9.7 s → 5.3 s: the Mods page and my CLI run both took the `classify` check.
