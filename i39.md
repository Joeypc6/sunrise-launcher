## The gap

The stack-mining differential (`tools/test_stack_mining_parity.py`) runs its Rust side through `stack_mining_probe`, an example of `client_probe` built with `-p sunrise-client-lib`. That crate never depends on gameplay, so the probe has no `Host`, `ServerGame` or `GameLevel`. Its pack rows compare the live 26.3 oracle with the item table the server builds for its world items (`Items::load_registry`), which proves the values, but not the path a mod reads them through: `BlockStates::is_correct_tool_for_drops` on a mod host (the generated `SideBlockTables` forwarder) and inside a block callback's level (`BlockTables::with_side_tables`). Today only a daily integration test covers that wiring. Found in #6312.

## Proposal

A gameplay-side probe (an example of a crate that depends on `sunrise-gameplay`) that boots a server game over the prepared resources, stages the harness's fixture pack as a world's tables, and answers each pack row twice: through the mod host's `BlockStates` and through `LevelHost::block_states` inside a `with_level` callback, printing the harness's row format. The harness then compares both outputs with the oracle bit for bit, and the same probe can add the suffocation reads (`BlockStates::is_suffocating`, `LevelRef::state_is_suffocating`) once the oracle answers `isSuffocating` against the pack.

## How to test

`tools/test_stack_mining_parity.py` runs the new probe for the pack rows beside the table probe; all three outputs (oracle, table, host and callback) match line for line.
