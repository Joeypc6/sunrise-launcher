## What and why

Fixes #4264. A mod's own screen could only open over the world. `mod_screen_open` over a container screen closes the menu, and Escape returned to the world. Applied Energistics 2 opens sub-screens over a menu's screen (`AESubScreen`, `switchToScreen`): the priority dialog, the crafting amount dialog and the crafting plan. The port draws these inside the container screen with screen hooks and hidden slots, so they have no own narration, no own focus, JEI does not see them as screens, and Escape closes the whole menu.

What the commit adds:
- `ScreensClientHost::mod_screen_open_over_menu(mod_id) -> bool`. It opens the mod's screen while a server menu's container screen is shown and keeps the menu open: no packet is sent, the window id, generation, slots and carried stack stay. `mod_screen_open` is unchanged and still closes a container screen it replaces.
- Return: Escape, `close_screen` and `mod_screen_close` go back to the same container screen (`setScreen(parent)`) with nothing sent. `close_mod_screen` does this when `mod_screen_menu()` is set.
- Ending: a server container close closes the sub-screen to the game. Any other screen replacing it (the death screen, a respawn) ends the menu as it ends a container screen it replaces. A stale window id or generation makes the marker stale, so no extra clean-up is needed.
- The covered container screen: covered, not closed, as NeoForge's `pushScreenLayer` covers a screen (not as `Gui.setScreen` replaces one). It gets no `screen_closing` and no `removed()`, and its own state (the recipe book page and search) stays. Its mounted widgets and the gamepad's focus go while it is covered; the pad focus is cleared when the sub-screen takes the screen and again on return, so no focus carries from one screen to the other. The sub-screen's `ScreenView.slots` is 0 (the menu's slots stay in the menu); `screen_slot`, `screen_pos` and `screen_hovered_stack` answer as with none open.
- Hooks: `screen_opening` fires from the container screen to the mod, then `screen_init_post`. On return: `screen_opening`, `screen_closing` for the sub-screen, then the container's `screen_init_post` (mounts its widgets as after a resize). A `screen_opening` answer of `Cancel` makes the call return false and changes nothing; `ModScreen` opens the answering mod's screen over the menu instead; `Vanilla(target)` returns false, opens that screen in place of the container screen and closes the menu with a container close, as `mod_screen_open`'s redirect does, and the container screen hears `screen_closing`.
- One level: a second call replaces the sub-screen (`screen_closing` fires for the replaced one) and Escape still returns to the container screen. The same mod's again is `true` with nothing fired.
- Refused (`false`, nothing changed): no window, a LAN guest's context, no player, a world loading, no server menu shown (the world, the player's own inventory, creative), or an overlay over the container screen. A `Cancel` answer also changes nothing.
- State: new `Game::native_mod_screen_menu: Option<(i32, u64)>`, read through `mod_screen_menu()` and `open_menu_key()`.

Not in this change: a server-side menu-to-menu switch (AE2's craft amount and confirm menus, priority, set stock amount), and client-side temporary slots for a sub-screen.
