## The gap

After #6312 (option (a), as decided on that PR), host block-state reads that need the world's data-pack tables read the owning side's tables, and level views built for block callbacks capture those tables once per view. Friction-part callbacks are the exception.

The motion view (`FrictionView` over `GameSide`) is built at `ordered_tick.rs:337`, before the friction-part subscriber check at `native_surface.rs:147`. It carries main's built-in tables, unchanged, so the stock motion path stays exactly as fast as before. As a result, inside a friction part's callback `BlockStates::is_suffocating` and `BlockStates::is_correct_tool_for_drops` ignore a world data pack and answer from the built-in tables. Everywhere else they follow the world's tables.

## Proposed fix

Attach the side's tables to the motion view only behind the friction-part subscriber check, with no per-call cost and no change to the stock motion path when no mod subscribes. Then a friction part sees the same answers as every other caller.

## Context

Found in #6312's review (point 2 of umceko's review: zero cost with no mods). #6312 states this as a known limit in the docs of the affected reads and links this issue.
