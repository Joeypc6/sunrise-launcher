## What a mod needs

To draw a grid of item icons beside a screen every frame without the per-icon cost dominating its frame budget. Example: a recipe viewer's item list (JEI) shows about 80 icons next to every container screen, and redraws them each frame although the page only changes when the player scrolls or types.

## Measurements

These are from a native mod on Dev ba1f24e, with 10 mods loaded, an offscreen client, the creative screen open, and the mod's own timers:

| | per frame |
|---|---|
| the mod's screen hooks, all | 349.1 µs |
| of which ~80 item draws | **328.7 µs (≈4.1 µs per icon)** |
| extra-area query | 4.9 µs |
| everything else (layout, cells, stacks, text; cached per page) | ≈15 µs |

The time per icon is spent entirely inside the host calls: `DrawContext::item(ItemKey, at, 16.0)` and `DrawContext::gui_draw_item_with(&ItemStack, at, None)` from `screen_render_pre`. The mod does no per-icon work of its own. It can't tell how much of the 4.1 µs is the call crossing and how much is the engine's draw. Both calls are unchanged on main 8207f6d6aa (`host/draw.rs`).

## What happens on main (8207f6d6aa)

- Each GUI item is one call: `DrawContext::item`, `gui_draw_item_with`, or `GuiCanvas::item` inside a draw scope. There's no call that takes many items, and no retained form.
- The engine already caches item renders the way vanilla does (`item_render/gui.rs`: `GuiItemAtlasSlots`, vanilla 26.3's `GuiItemAtlas` / `DynamicAtlasAllocator`). So drawing itself should be cheap, and the per-call resolve or crossing is probably what costs. A trace span around the host's GUI item draw would show which.
- `InstanceGroupRef` and `prepared_item` give retained draws for block-entity world rendering, but nothing does the same in GUI space.

## Proposal

Either form fits; the first is the smaller change:

```rust
/// Draws every `(stack, at)` in order, as that many `gui_draw_item_with(stack, at, None)` calls
/// would, at 16 px. One host call: the render-state resolves and atlas lookups run back to back.
fn gui_draw_items(&mut self, items: &[(&ItemStack, [f32; 2])]);
```

or a retained batch that the mod builds when its page or search changes and replays each frame:

```rust
fn gui_item_batch(&mut self, items: &[(ItemStack, [f32; 2])]) -> Result<GuiItemBatchRef, GuiDrawError>;
fn draw_gui_item_batch(&mut self, batch: GuiItemBatchRef, offset: [f32; 2]) -> Result<(), GuiDrawError>;
fn destroy_gui_item_batch(&mut self, batch: GuiItemBatchRef);
```

Animated items (a compass, a clock, an enchantment glint) would still resolve each frame inside a replayed batch, as `GuiItemAtlas` skips them.

## Vanilla reference

- Vanilla's creative grid also draws icons one by one (`GuiGraphics.renderItem` → `GuiRenderer` / `GuiItemAtlas.getOrUpdate(TrackingItemStackRenderState)`), but inside the game, with no cost crossing into a mod. The request is about the mod path, not parity.
