1. **`Vanilla` answer leaves the menu open.** Fixed in `open_mod_screen_over_menu` (base.rs, the `ScreenDecision::Vanilla` arm): it now fires `screen_closing` for the container screen (a sub-screen's was already fired with the decision), calls `close_replaced_screen_for_mod()` as `mod_screen_open` does, then opens the target. The rustdoc, the change note and the PR body now say so (a `Vanilla` answer returns false but changes what shows).
2. **Covered container screen's lifecycle.** I picked the `pushScreenLayer` contract, which is also what the issue asked for: the container screen is covered, not closed. It gets no `screen_closing` and no `removed()`, and its own state (recipe book page, search) stays. Its mounted widgets go while it is covered and `screen_init_post` runs again on return, as after a resize, so a listener seeing that hook twice is the stated behaviour. `screen_opening` still fires for the sub-screen, so a mod can veto or redirect it. Focus: `pad_clear_focus()` runs when the sub-screen takes the screen (base.rs, before the marker is set) and on return (`close_mod_screen`, world_helpers.rs), so no focus carries from one screen to the other. The recipe UI is deliberately not reset: that screen is kept. This is in the trait rustdoc, the change note and the PR body, and tested: `a_mod_screen_over_a_menu_keeps_it_and_escape_returns_to_its_screen` sets a pad focus before the open and before the return and checks it is cleared.
