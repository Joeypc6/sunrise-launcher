## What and why

Closes #7106.

**Repro.** On main (client built from 70d397565a; no skin or profile code has changed since), offscreen, with the skin served from the local skin cache and a local fixture services server (`SUNRISE_API_DISCOVERY`), so nothing reached Mojang. Most custom heads already draw their profile's skin: placed, in the hotbar and hand, worn by an armor stand, and worn by the player in third person. That holds for single player and for a remote `sunrise-server`, for a `textures`-property-only profile, a name + id + properties profile, a name-only profile (`"Name"` or `{name:"Name"}`), an id-only profile and a `texture` patch. ba1f24e behaves the same.

What fails is the **old map form of `properties`**: `/setblock ~ ~ ~ player_head{profile:{properties:{textures:["<base64>"]}}}` draws the default skin. The same profile on an item (`player_head[profile={properties:{textures:[...]}}]`) draws correctly, because the item component is rewritten to the list form when it is decoded. A skull's block entity keeps the NBT as written: from `/setblock`, a structure, or a world saved that way. `profile_lookup` read `properties` only as a list. So the skull had no skin URL. With a name and the map form, `dynamic_nbt` also saw "no properties", so the head was resolved by name as a `Dynamic` profile when it should have been `Static`.

Vanilla reads both: `ResolvableProfile.CODEC` takes `properties` through `ExtraCodecs.PROPERTY_MAP`, which decodes either a list of `{name, value, signature}` or a map from a name to its unsigned values. Sunrise already reads both forms elsewhere (`sunrise-sim`'s `entity_nbt.rs` and `sunrise-gameplay-common`'s `native_text_nbt/profile.rs`).

**Fix** (`crates/sunrise-level/src/profile_lookup.rs`):
- `profile_skin_url_nbt` (the skull's `SkullSkin::of` download) finds the first `textures` value in either form.
- `dynamic_nbt` and `parse_profile` count a map with any value as properties (`PropertyMap.isEmpty`), so such a profile is Static. A map with no values, such as `{}` or `{textures:[]}`, is still no properties, so a name-only profile stays Dynamic.
- `parse_profile` (JSON `minecraft:profile`) reads the map form too, as an object of arrays, so both readers agree. This one is not needed for anything seen today: items and worn heads reach the client in list form. An armor stand summoned with map-form equipment keeps the map in its NBT but already drew the skin on main.

List-form, string and name/id profiles go through the same code as before.
