## 1. A reduced build reported up to date for the whole set (review point 2)

**Cause.** `pipeline` names a build with `version_for(.., &requested)`: every requested mod, including those this attempt leaves out. A retry that leaves a mod out (`isolated`, after the check or the compile blames it) is installed under the same version as the whole set. A later plan of the whole set that passes the fit check computes that version, finds `.installed` there (the existing-build branch only checks the marker) and says "Up to date" with the mod missing. The Mods page then lists it as left out. A profile's exact build refuses it, but only after the build.

**Fix.** `version_for` takes the left-out mods and salts its hash with their sorted ids when there are any (`src/native_mods.rs:735`). A whole set's version is the same as before, so no installed build is rebuilt.

**Regression test.** `native_mods::tests::a_build_that_leaves_a_mod_out_never_has_the_whole_sets_version` names a two-mod set as `pipeline` does (`kept_mods`, then `version_for` over every requested mod) with and without one mod left out, and requires the two versions to differ.

**How I know it fails on `main`.** Its signature only exists on the branch, so I ran it once in the build queue with the salt taken back out of `version_for`, leaving the bytes hashed the same as `main`'s. It failed with `left: "native-aaaaaaa-448598e378db"`, `right: "native-aaaaaaa-448598e378db"`: one version for both builds. Restored, it passes.  `version_for`'s other inputs are unchanged by the commit, so on `main` the two builds have exactly that one version.

An older launcher's reduced build already installed under a whole set's version keeps that version. The second commit never takes it as the whole set without planning, and never writes reuse evidence for it, because its record names mods left out. It is still planned as on `main`.

## 2. The fast path proves the installed build (review points 1 and 2)

`.native-inputs`, the `native-inputs-v1` key and the 7-character prefix scan are gone. `version_for` is the one identity.

- **A stable view.** The lookup works on private copies of the mods: the planned path's own `mods.incoming` copies in `pipeline`, or a `.native-input-*` copy before the profile check. From them it works the version out as planning does (`reuse::derive`, `src/native_mods/reuse.rs:298`):
  - the kept and left-out mods;
  - the override-aware dependency graph;
  - the revision;
  - the pins, through the plan's own `mixins::read_pins`, but from SDK indexes already kept on disk (`sdk_cache::kept`; nothing is fetched);
  - `materialize` on the copies, and the horizon-mixins key with kept commit dates;
  - then `version_for`.

  The candidate is the folder with exactly that version. The plan and the lookup hash the same kind of bytes (staged, materialized copies).
- **Evidence from the verified plan** (`reuse::record`, reuse.rs:228). Written beside a client build once it is installed, or used again. It holds:
  - `Image`: what changes the build without being in its version. Each kept mod's pin, the Cargo link order the tool gets, the override-aware dispatch order (now returned by `resolve_build_dependencies`, `src/native_mods.rs:1431`, not checked and dropped), the left-out ids, and the SHA-256 of each SDK index the plan read, from the `Sdk` values it consumed (and the developer SDK's index).
  - `Admission`: what only admitted the plan. The launcher version (its checks), the base and starting release, an exact profile build, and `SUNRISE_SDK_BASE`. One build keeps up to 8.
  - A seal of the installed game (`managed_play::Artifact::capture_at`: the executable, `native-mods.json`, `deps/`, the native trees and each library beside the game).

  It is written only when the installed folder holds the plan (`Contents::installed_in`, reuse.rs:153), in the existing-build branch too: `native-mods.json` names the revision, the starting release, the horizon-mixins key, the profile and the left-out set; `native_status::included` (Play's check) lists exactly the kept mods at their versions and digests; and `sunrise-native-mods/` holds exactly their copies. The file is written whole or not at all, and it isn't carried over to builds made from this one.
- **The proof** (`reuse::lookup`, reuse.rs:380). The evidence must name the version and hold an equal `Image` and `Admission`, the contents must hold, and the seal must match. Then the profile (mod list, content packages, overrides, kept indexes) is read again and the mods' folder is compared with the copy. A change while the build was proved misses.
- **Seal, and what's missing.** Native installs publish no receipt like `Artifact::record_archive` / `record_sdk`. So the seal is taken right after `publish_build`, or, for an older launcher's build, at its first reuse after the contents check. A change to an image before that first record can't be seen. A publish-time receipt belongs with the install path, and can be a follow-up.

## 3. Reuse before the default entry's SDK check (review point 3)

`build` (the Mods page and the CLI) now tries `reuse::before_planning` before `select_build_profile` → `planning::classify`, with the profile the automatic choice resolves to (`AUTOMATIC`), at `src/native_mods.rs:2432`. Whatever stops it (an unprepared base, a duplicate id) finds nothing, so errors are said as before. `pipeline` tries again after copying the mods (`src/native_mods.rs:1643`), for an explicit profile and for `build_exact_client`. A server build is always planned.

The `Checking` step aside, `classify` ran `check_projects` → `check_all` on a signed base even when `pipeline` later found the build. That is why #622's Windows run went only from 9.7 s to 5.3 s.
