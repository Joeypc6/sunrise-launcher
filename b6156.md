## What and why

Fixes #6023. Since the scoped GUI drawing change, an item decoration (`ItemPart::item_decorations`) draws into a `GuiCanvas`, and `GuiCanvas` had no way to draw an entity. A decoration could no longer show a mob over its icon. The consumer waiting on this is Hostile Neural Networks' data model item, whose Java `DataModelItemModel` shows its mob scaled into the slot. On Sunrise it falls back to the spawn egg.

The fix adds a fallible entity primitive to `GuiCanvas`, built on the existing `DrawContext::entity` types rather than the issue's loose `(entity_type, at, size, yaw, pitch)` signature:

```rust
fn entity(&mut self, entity: &GuiEntity, view: GuiEntityView) -> Result<(), GuiDrawError>;
```

- `GuiEntity::kind("minecraft:zombie")` / `with_data` draws a default-state client entity of a type, with no world entity needed. It is made once and kept while drawn every frame, as `DrawContext::entity` does. `GuiEntity::existing` draws a client entity.
- `view.rect` is in the canvas's local GUI pixels. The entity is drawn exactly as `DrawContext::entity` draws it (`Game::native_draw_entity`), then moved by the canvas's current pose with the same per-vertex finiteness check every canvas primitive uses. Under a pose that keeps the axes its own depth pass is cut at the posed box's screen bounds. Under a turned pose the model's geometry is cut to `view.rect` in local pixels before the pose (`HudBatch::crop_since`), so it can't spill from the rotated box into the corners of its bounds; the group's scissor applies over it either way, independently.
- `GuiDrawError` gains `Entity(GuiEntityError)` (non-exhaustive enum; `Display` and `source`). `GuiEntityError::Unavailable` maps to the canvas's own `GuiDrawError::Unavailable`. A canvas with no game (the renderer-only fixture) answers `Unavailable`. A pose that takes the box or a vertex out of finite range answers `NotFinite`. A refused call leaves the batch as it was (the canvas's `draw_scope` rollback).

Tests:
- `entity_needs_a_game_and_refuses_an_undrawable_view_first` (verify tier): with no game, a valid view returns `Unavailable` and an empty box returns `Entity(BadView)`. Nothing is drawn.
- `an_item_decorator_canvas_draws_a_mob_in_its_pose_and_scissor` (daily, child-process: the whole fixture runs in a fresh child selected by this test's exact name, as `scoped_items_keep_the_seed_and_draw_decorations_outside_the_squeeze` does): a zombie drawn through an item-decorator canvas (`decorating: true`) inside a `Translate(40, 30)` scope with a 16×16 slot scissor:
  - It gives exactly `DrawContext::entity`'s vertices, moved by the pose, with the same UVs, colours and depths.
  - The run is scissored to `[40, 30, 56, 46]`, and its `Depth` pass is cut at the posed box.
  - An empty box, an overflowing size and an unknown type return their `Entity(..)` errors. A pose scaling the box out of range returns `NotFinite`. The batch's vertices and blends are unchanged after these refusals.
  - A model 40 px a block (overflowing its 16 px box) under `Translate(90, 70)` then `Rotate(0.6)`, inside an outer scope whose scissor is screen `[60, 40, 120, 100]`: every drawn vertex, taken back through the pose, lies in the local box; the run's scissor is the outer one, not the box's bounds; the depth pass is cut at the posed box's bounds.

## Layer

## Vanilla reference

`InventoryScreen.extractEntityInInventoryFollowsMouse` (vanilla 26.3) for the mouse-following look, and `GuiGraphicsExtractor.entity` given the render state and a rotation for a fixed turn (`GuiEntityLook::Turned`); `DrawContext::entity` already follows them. On NeoForge, `IItemDecorator.render(GuiGraphics, Font, ItemStack, x, y)` gets the full GUI renderer, entity rendering included, which is what HNN's data model uses.
