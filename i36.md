## What a mod needs

A block whose world colour comes from its block entity rather than its block state: a dyed chest, a tinted glass block, a painted pipe. The colour is any RGB, so it can't be a block-state property. In Java the mod registers a `BlockColor` (26.3: a `BlockTintSource`) whose `colorInWorld(state, level, pos)` reads the block entity at `pos`. It uses `level.getBlockEntity(pos)`, or on NeoForge the block's `ModelData` (`level.getModelData(pos)`). When the colour changes, the block entity asks for a re-render.

Example: Tinkers' Construct's dyed chests (the Tinkers' chest and the part chest) keep their colour in the block entity. The item tint works in the port, but every placed chest shows the default colour, because the block's tint source can't learn which colour that chest has.

## What happens on main (ba8bf2d2f4)

- `BlockTintSource::color_in_world(state, metadata, level: &dyn BlockAndTintGetter, pos)` (`block/block_tint.rs`) gets the meshed region. Its docs say: "Block entities are not part of the region." It reads block states, fluids, light and biome tints only.
- `ClientRenderClientHost::set_block_extra_models(pos, models)` (#2763 / #2771) lets a client mod attach per-position models that the mesher draws, but they are coloured by the block's same tint sources. A per-position colour would need one model per colour.
- #961 (baked model edits and ModelData) designs ModelData evaluated on the client thread before geometry is frozen. Its acceptance matrix covers model selection, not tints, and nothing hands ModelData to a tint source.
- The only workaround is a block entity renderer that draws the whole block every frame, which loses chunk meshing.

## Proposal

Per-position tint data that a client mod sets and the mesher reads, alongside the extra models from #2771:

```rust
/// Client: per-position values for this block's tint sources (at most a few u32s), stored with
/// the client's chunk column as the extra models are. Setting a different list re-meshes the
/// section; cleared when the block state at `pos` changes, the column unloads or the level changes.
fn set_block_tint_data(&mut self, pos: [i32; 3], data: &[u32]) -> Result<(), BlockTintDataError>;

// BlockAndTintGetter, read on the meshing workers with no mod code run beyond the tint source:
/// The values a client mod set for `pos` with `set_block_tint_data`; empty when none.
fn block_tint_data(&self, pos: [i32; 3]) -> &[u32];
```

The mod sets the colour from its block entity's client sync, for example in `block_entity_data_received` or on load. The tint source returns `level.block_tint_data(pos).first()` or its default. That keeps workers free of block-entity access. If #961's ModelData reaches tint sources instead, this issue can be closed against it, provided tints are part of its contract.

## Vanilla / NeoForge reference

- `BlockTintSource.colorInWorld(BlockState, BlockAndTintGetter, BlockPos)`; `BlockAndTintGetter` extends `BlockGetter`, whose `getBlockEntity(pos)` the section region (`RenderSectionRegion`) answers from its snapshot of the chunks.
- NeoForge: `IBlockGetterExtension.getModelData(pos)` / `ModelDataManager`, `BlockEntity.requestModelDataUpdate()`.
