## What and why

Fixes #6035. A mod cannot ask another block state for three answers that vanilla blocks give: how much light it stops, whether an entity inside it suffocates, and whether a mob may spawn on top of it. Applied Energistics 2's cable bus needs the light dampening of a state and falls back to vanilla's default rule. Elevator is camouflaged as another block and answers suffocation and spawning with the held state's answers; its port works them out from shapes and a list of see-through blocks.

On `BlockStates` (both sides, state alone, no position):
- `light_dampening(state) -> Option<u8>`: `BlockStateBase.getLightDampening()`, 0 to 15 (stone 15, water and leaves 1, glass and air 0). Read from the exported per-state facts.
- `is_suffocating(state) -> Option<bool>`: the block's own `isSuffocating` predicate from the level's suffocation rules, the same table the position read uses. On the server that is the open world's (its data packs' `#minecraft:causes_suffocation`), through a host and inside a block callback's level alike (a friction part's level reads the built-in one, #6626); on the client the built-in one until the client receives the world's tables (#6597). `None` when the answer needs a position or a block entity: a closed shulker box, or a shape a block entity publishes or an offset moves. New `SuffocationRegistry::constant(state)` gives the constant answers.
- `is_valid_spawn(state, entity_type) -> Option<bool>`: `BlockState.isValidSpawn` from the table natural spawning reads. Leaves admit ocelots and parrots, ice polar bears, magma blocks only fire immune types, and a block's declared spawn rule is already in the flags. `None` for an entity type with no spawn species. The entity type resolves through a species table built once (`species::of_vanilla_id`). Natural spawning's surface check is split into `spawn_state_valid`, and `spawn_rules::is_valid_spawn_on` is the new public entry.
- All three return `None` for an unknown state, as the other reads in `BlockStates` do.

On `LevelRef` (both sides):
- `state_is_suffocating(host, state, pos) -> Option<bool>` (state then position, as `visit_block_shape` takes them): `BlockState.isSuffocating(level, pos)` for a supplied state at a position, which need not be the block stored there, so a camouflaged block asks about the state it shows. It runs the suffocation rules entities use (`SuffocationRegistry::is_suffocating` over the level's block entities): a shulker box suffocates unless the `ShulkerBoxBlockEntity` at `pos` is not closed, no block entity there counting as closed (`Blocks.shulkerBox`'s predicate); a published or offset shape is tested at `pos`. Reads active and parked server levels and the client's current level, never loads chunks; `None` for an unloaded or out-of-height position, a stale level, an unknown state and a collision query error.

### The generated host forwarders read the side's tables (decided on #6312)

After the gameplay split (#6527) the data-pack tables (`WorldTables`: the world's suffocation rules, its item table with the block tags its packs bind) belong to each side's state, and every generated `ServerGame`/`ClientGame` forwarder of a `BlockStatesBackend` read called `BlockTables::of(&self.common)`, the game's own tables. **This generator change was decided on #6312 by umceko's reviewer with Ari's agent** (option (a): route the reads that need the world's tables to the owning side; not (b), a copy of the world's tables in `CommonGame` that would have to stay in sync across data-pack reloads; not (c), dropping the point).

- `crates/sunrise-mod-api-gen/src/host.rs`: a table read with a host row in `gameplay-routes.toml` forwards to that row's callee, with the same borrow and route checks an inherent read's row gets (`routed_call`, shared by both). A table read with no row keeps `BlockTables::of(&self.common)`.
- `crates/sunrise-mod-api-gen/gameplay-routes.toml`: server and client rows for the two reads that need the side's tables:
  - `BlockStatesBackend::block_state_is_suffocating`: the level's suffocation rules (`GameItems::level_suffocation`, the world's `#minecraft:causes_suffocation`), the rules `LevelCollisionBackend::level_state_is_suffocating` already read (it was routed to the side by the split). Both suffocation reads now use one table.
  - `BlockStatesBackend::block_state_correct_tool_for_drops`: the side's item table (`GameItems::items`), whose block tags a world pack rebinds (`#minecraft:mineable/pickaxe`), the table the game's own harvest check reads (`held_items.rs`). Before, a world pack changed the game's harvest but not this answer; with no world packs the answer is unchanged. Change note `block-state-reads-side-tables.toml`.
- Callee: `SideBlockTables` in `native_block_tables.rs`, a trait over `SideGame` with `#[inline(always)]` default methods, so no new replaceable `Game` method. It builds the same `BlockTables` view a level view holds, with the side's table, and calls the one body of each read.
- Nothing is copied into the common state: `CommonGame` and `Resources` gain no field. `BlockTables`, a borrowed view, holds two references to the side's tables (below).
- No cost with no mods: only a mod's call reaches a forwarder.

### Block callbacks read the same tables; the motion views keep main's code

A part also reads `BlockStates` through a level view: the `GameLevel` a block callback gets (`LevelHost::block_states`), and the `GameSide` a motion tick lends a friction part.

- `BlockTables` holds `side: Option<SideTables>` beside main's two references. `BlockTables::new` stores `None` and resolves nothing; `with_side_tables` (`#[inline(always)]`) sets the side's suffocation rules and item table, and the two reads take them, else the game's own.
- The block callback's level takes them once, where the `GameLevel` is built: the server's (`game_server.rs`, reusing the item table it already resolves for its own `items` field) and the client's (`world_ops_client.rs`; the client holds no world tables, so the game's own rules). Inside a block callback, `BlockStates::is_suffocating` and the correct-tool read answer as the side's host does.
- The motion views are main's code: `game_side!`, `server_game_side!`, `client_game_side!` and the client's mob and bobber `GameSide` build `BlockTables::new` exactly as on main, so the stock motion path (the experience-orb loop at `ordered_tick.rs:337` and its siblings) resolves nothing new.
- A friction part's level is that motion view. The friction-subscriber check (`native_surface.rs`, `friction`) comes after the view is built, and the view has no route back to the side's world tables, so a friction part reads the game's own tables for these two reads. Limit, #6626; the docs of the reads say so.
- Cost on a read: one `Option` check inside a mod's read (`side` set or not); no lookup.
- `BlockTables::of` elsewhere (fluid ticks, waxing, ray clips, fluid looks) keeps the game's own tables: those callers read no suffocation or tool rule.
- The other `BlockTables` reads read nothing a world's data packs change, or read it through the shared `Resources` (the `block_transformer` table that `Resources::set_transformers` publishes for the open world on both sides, the installed `neoforge:waxables` maps): they stay on the common view. `block_state_poi_type` reads the built-in POI table; the world's copy differs only by the professions native mods declare, not by data packs, so it stays as it was.
- Generated output: checked: the generator was built at 39826d884c (before) and at be9a6499e6 (the generator change), and both wrote the common, server and client generated host files; `diff -ru` of the two outputs differs in exactly two files, the client's and the server's `game_host_generated.rs`, and in exactly four functions, `block_state_is_suffocating` and `block_state_correct_tool_for_drops` in each side's `BlockStatesBackend` impl (each now calls `<ServerGame|ClientGame as SideBlockTables>::...` where it called `BlockTables::...(&BlockTables::of(&self.common), ...)`). The common package's output and every other read are byte-identical.

### Known limits (follow-ups)

- **Friction parts (#6626).** A friction part's level is the motion view, which keeps main's code and the game's own tables, so inside a friction callback both reads answer from the built-in rules and tags. Follow-up: route the side's tables to the friction view behind the subscriber check without a per-entity cost on the stock path.

- **The client's tables (#6597).** The client host and the client's level views can't follow a pack yet: the client's state has no world tables (`ClientGame::client_world_tables` returns `None` at `world_entry_client.rs:29`, as the split left it), so on the client both reads use the game's own suffocation rules and item table, while vanilla's client binds the tags the server syncs. The docs of the reads say so. The new test checks that the server follows the pack and asserts the client's built-in answers. Follow-up, #6597: build the client's world tables from the server's synced tags when they arrive and on reload, and return them from `client_world_tables`; the routed forwarders and the client's level views then follow with no further change, and the test's client half flips to the pack's answers.
