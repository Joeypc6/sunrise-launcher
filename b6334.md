## What and why

Fixes #6127. A mod cannot read an entity type's default width, height and eye height without spawning one. Ender IO's powered spawner picks a free spot for the next mob by testing the type's box against blocks and entities, and sizes its spawn range by the mob's height. Its port spawns the mob, checks it and takes it back the first time a kind is used; that spawn fires join and leave hooks other mods see.

What the commit adds:
- `ItemsHost::entity_type_dimensions(entity_type) -> Option<EntityTypeDimensions>`, beside `entity_type_default_attribute`, side both. It is `EntityType.getDimensions()`: the type's registered size, before any `entity_size` answer for a live entity, a baby's size, a scale attribute or a pose.
- `EntityTypeDimensions { width, height, eye_height }` (all `f32`), read-only for mods.
- The game reads it from the entity type rows of its resources. The id is normalised as `Identifier.parse` does (`zombie` is `minecraft:zombie`). `None` for an unregistered type or one with no size row.
- The read is `getDimensions()` and does not carry `EntityType.spawnDimensionsScale`. The doc and the change note state the spawn box: `EntityType.getSpawnAABB` is `spawnDimensionsScale * width / 2` either side of x and z and `spawnDimensionsScale * height` up from y, with the scale 4.0 for the slime and the magma cube, 2.0 for the sulfur cube and 1.0 otherwise, so a mod testing a cube mob's spawn box applies it itself. No helper for the box is added.
- `ItemsHost` only, like the size's source (the resources' entity type rows); `entity_type_default_attribute`'s reload and setup context forwards read a table the game publishes once its attribute catalog is built, which the sizes are not in.
- The proposal's `fixed` field is not added.
